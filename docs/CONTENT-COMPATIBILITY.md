# 内容格式与 Hugo 迁移兼容说明

本文档是新站内容格式的维护基线。目标是让现有 Hugo 文章尽量原样放入
`content/`，同时避免新站继续依赖整个 Hugo 主题。

## 处理次序与当前状态

| 次序 | 格式 | 当前处理方式 | 状态 |
| --- | --- | --- | --- |
| 1 | 基础 Markdown、代码围栏、链接、图片 | 本地渲染并转义不安全内容；代码按语言高亮、可复制、可横向滚动 | 已支持 |
| 2 | GFM 表格、删除线、任务列表 | 转为语义化表格、`del` 和只读复选框 | 已支持 |
| 3 | 脚注、引用式链接 | 生成编号、回链和文末脚注区 | 已支持 |
| 4 | Hugo `notice` 短代码 | 转为新站自己的提示框组件 | 已支持 |
| 5 | Hugo `imgloop` 短代码 | 转为无 JavaScript 的横向滚动图片集 | 已支持 |
| 6 | 安全的文章内 HTML | 支持 `details`、`summary`、`kbd`、`mark`、`br`；`center` 转为 CSS 类 | 已支持 |
| 7 | 数学公式 | 检测到公式时按需加载 KaTeX 0.18.1 与官方 auto-render 扩展 | 已支持 |
| 8 | 文章内音频 | `audio` 短代码按需加载本地 APlayer；网易云模式额外按需加载本地 MetingJS | 已支持 |
| 9 | 未知 Hugo 短代码 | 页面显示兼容提示，构建终端输出文件和格式告警 | 可追踪 |
| 10 | 多级无序/有序列表 | 根据两个以上空格或 Tab 缩进生成嵌套 `ul` / `ol` | 已支持 |
| 11 | 列表项内引用 | 在列表项下缩进两个以上空格后使用 `>`，生成属于当前条目的引用 | 已支持 |

## 推荐的文章头部

```md
---
title: 文章标题
author: Huang
date: 2026-07-14
pinned: true
description: 可选；不写时自动提取正文摘要
slug: optional-custom-url
tags:
  - AI
  - Agent
---
```

`pinned: true` 会把该内容置顶到首页对应栏目；省略该字段或写成 `false` 时按普通内容处理。首页先按日期从新到旧展示全部置顶内容，再用最新的非置顶内容补足三项；如果置顶内容超过三项，则全部展示。该字段不改变归档页的日期顺序，也不在归档页或详情页显示置顶标记。

当前生成器通用字段包括 `title`、`author`、`date`、`description`、`slug`、`tags` 和 `pinned`。
`author` 与 `tags` 会显示在文章标题下方；`title` 与 `date` 必填。

详情页会自动根据对应 Markdown 文件的 Git 历史显示“修改于：日期”和“已修改 x 次”，不需要增加 Front Matter 字段。“修改于”取最近一次提交日期；修改次数等于涉及该文件的提交数减一，因此首次创建不计为修改。本地尚未提交的保存不会计数，完成提交后下一次构建会自动更新。

## 按年份管理文件

三个栏目目录都会递归读取 `.md` 文件，因此可以按年份继续分层：

```text
content/writings/2026/example.md
content/readings/2026/example.md
content/projects/2026/example.md
```

年份文件夹不会进入文章 URL。URL 仍由 Front Matter 的 `slug` 决定；没有填写 `slug` 时，
使用文件名。栏目内的 `slug` 必须唯一，发生重复时构建会明确列出冲突文件。

## 推荐写法

### 首页可选摘要

Prompt、写作和阅读栏目统一读取 Front Matter 中的 `description`。填写时，摘要显示在首页文章标题下方：

```md
---
title: 示例文章
date: 2026-07-21
description: 这段文字会作为首页摘要。
---
```

没有填写 `description` 时，首页只显示标题，不生成摘要元素，也不预留摘要高度。

### 项目列表

项目列表使用与其他栏目一致的日期、标题、摘要和箭头结构，其中摘要读取 `description`。点击任意项目行会进入该项目 Markdown 生成的正文页面。

### 多级列表

子级前使用两个空格或一个 Tab。无序列表与有序列表可以交叉嵌套：

```md
- Claude
  - Web 网页
    1. Chrome
```

引用块中的列表可以在条目之间保留空白引用行，渲染器会将它们识别为同一个“宽松列表”，
因此 `1、2、3` 不会被拆成多个从 1 开始的列表。以其他数字开头的有序列表也会保留起始编号。

列表项下也可以嵌入引用。`>` 前至少保留两个空格，无序列表和有序列表的写法相同：

```md
1. 文本
  > 这段引用属于第一条内容。
2. 后续文本
```

### 行内强调

单个星号生成斜体，两个星号生成粗体；强调语法放在链接文字中也会正常解析：

```md
这是 *斜体* 和 **粗体**。

电影链接：[*Her*](https://example.com/her)
```

### 代码块标签与文件名

普通代码围栏会自动把代码类型显示在工具栏左侧：

````md
```python
print("Hello")
```
````

如果需要显示文件名，可以在语言后添加 `label` 或 `title`：

````md
```python label="app.py"
print("Hello")
```
````

也支持更简短的 `` ```python app.py `` 写法。标签只负责显示，围栏开头的 `python`
仍负责语法高亮。工具栏只保留标签和“复制”；当前不加入“原始 / 渲染”，因为代码围栏
本身就是原始内容，而渲染视图只对少数 Markdown 或 HTML 示例有意义。以后若有明确案例，
可将其作为单个代码块的可选能力，而不是所有代码块的固定操作。

`python`、`javascript`、`ascii` 等围栏首词是“渲染类型”，不是任意标题。若要显示中文标题或带空格的标题，
推荐把内容按 `text` 渲染，再使用 `label` 明确指定显示文字：

````md
```text label="流程"
输入 → 处理 → 输出
```

```ascii label="ASCII 图"
┌──────┐
│ Demo │
└──────┘
```
````

为兼容已经迁移的文章，`` ```流程 ``、`` ```示意图 `` 与 `` ```ASCII 图 `` 也能直接显示相应标签；
不过新文章推荐使用显式的 `label="..."`，这样“如何渲染”与“显示什么标题”更容易维护。

### Prompt 展示块

需要把一段可直接复制给大模型的文字展示为 Prompt 卡片时，使用独立的 `prompt` 围栏：

````md
```prompt
在 2—3 年后，我现在反复纠结的这件事最终失败了，或被证明不重要。
失败最可能不是因为能力，而是因为哪三种被我合理化的行为或假设？
```
````

页面会显示带 `<> Prompt` 标题栏、复制按钮和无衬线正文的专用组件。旧文章中的 `` ```提示词 ``
写法也会得到同样的效果，但建议新内容统一写成英文 `prompt` 触发词，以便与代码语言标识区分。

需要展示 AI 的回答时，使用结构相同但颜色稍浅的 `React` 围栏：

````md
```React
这是 AI 返回的内容。
```
````

旧文章中的 `` ```回应 `` 会自动按 React 块渲染。Prompt 与 React 的正文均使用接近 Codex
界面的无衬线 UI 字体，适合并列展示一轮对话中的用户输入与 AI 输出。

如果要标记回答来自哪个模型，可以在 `React` 后添加模型标签。为兼容已有草稿，
`lable-`（旧拼写）与 `label-`（正确拼写）都会生效；新文章更推荐可读性更好的
`model="..."`：

````md
```React lable-GPT
这是 GPT 的回答。
```

```React label-Claude
这是 Claude 的回答。
```

```React model="Gemini"
这是 Gemini 的回答。
```
````

三个模型会分别只显示对应的 GPT、Claude、Gemini 图标与名称，不再额外显示 `REACT`。
裸写 `` ```React `` 时不指定模型，继续显示通用图标和 `React`，不会被自动归类为 GPT。

### Markdown 强制换行

普通段落和引用中，行末保留两个空格，下一行就会在同一段内强制换行：

```md
> **规划（Reasoning）**：第一行。\
> **反应（Acting & Observing）**：第二行。
```

示例使用行末反斜杠 `\`，是为了让不可见的换行标记更容易辨认；把它换成两个行末空格也有同样效果。
若希望生成两个独立段落，则在两行之间保留一个空白行。

### 提示框

旧文章可继续使用 Hugo 写法：

```md
{{% notice warning "注意" %}}
提示框中的正文仍可使用 Markdown。
{{% /notice %}}
```

类型支持 `content`、`info`、`warning`、`success`、`danger`。

### 图片集

为了兼容旧文，可以继续使用逗号分隔地址：

```md
{{< imgloop "https://example.com/1.png,https://example.com/2.png" >}}
```

新站不再加载旧主题中的 Swiper 3.4.2。图片集使用 CSS `scroll-snap`，减少脚本、
版本和安全维护成本。

### 音频

音频短代码应写在文章的 Markdown 正文里，也就是 `content/` 下某篇 `.md` 文件
头部第二个 `---` 之后。三个栏目都可以使用：

```text
content/projects/年份/文章.md
content/writings/年份/文章.md
content/readings/年份/文章.md
```

不要把短代码写进 YAML 头部，也不要写进 `public/` 或生成后的 `dist/`。

#### 1. HTTPS 音频直链

适用于可以直接返回音频内容的 MP3、M4A/AAC、Ogg 等地址：

```md
{{< audio title="歌曲名称" artist="艺术家" url="https://example.com/audio/song.mp3" cover="https://example.com/audio/cover.jpg" link="https://example.com/song" >}}
```

远程服务器需要允许浏览器跨域读取，并正确支持音频文件请求。音乐平台的歌曲
网页不是音频直链，不应当按这种方式使用。

#### 2. 站内音频文件

先把有权公开的音频文件放入 `public/audio/`，正文使用以 `/audio/` 开头的地址：

```md
{{< audio title="歌曲名称" artist="艺术家" url="/audio/song.mp3" cover="/audio/cover.jpg" >}}
```

#### 3. 网易云音乐 ID（推荐）

单曲使用 `type="song"`：

```md
{{< audio server="netease" type="song" id="28226058" >}}
```

网易云模式还支持 `playlist`、`album`、`artist`，例如歌单：

```md
{{< audio server="netease" type="playlist" id="60198" >}}
```

为了兼容已经写好的内容，本站也会自动识别网易云页面 URL：

```md
{{< audio url="https://music.163.com/#/song?id=28226058" >}}
```

新内容优先使用明确的 `server + type + id` 写法，便于检查和长期维护。

#### 字段说明

- 直链或站内模式必须填写 `url`。
- 网易云模式必须填写 `server="netease"`、`type` 和数字 `id`。
- 网易云模式会从平台获取曲名、艺术家、封面和歌词；正文只需提供 `server`、`type` 和 `id`。
- 直链模式的 `title`、`artist`、`cover`、`link` 均可选；`link` 只负责提供原始页面入口。
- 网易云模式不显示额外的来源入口，也不读取 `title`、`artist`、`cover` 或 `link`。
- `cover` 和直链 `url` 只接受 HTTPS 或以 `/` 开头的站内地址。
- 不支持 `http://`、电脑本地磁盘路径或 `javascript:` 等地址。

播放器不会自动播放。只有包含该短代码的详情页才会加载本地固定版本的
APlayer 1.10.1。只有使用网易云模式时，页面才会额外加载本地固定版本的
MetingJS 2.0.2。直链模式在 JavaScript 失败时保留浏览器原生 `audio` 控件；
网易云解析失败时显示简短错误提示，不影响文章其他内容。平台歌曲仍可能因为
版权、地区、会员限制或解析服务变化而无法播放。

播放器成功加载后，曲名与艺术家由 APlayer 自身展示。网易云模式不会生成额外
图注或来源链接，播放器之后的正文会按正常文章间距继续排列。

网易云模式会异步读取并显示平台歌词。对于网易云标记为纯音乐的曲目，歌词区
会显示平台返回的“纯音乐，请欣赏”。直链与站内文件模式目前不解析歌词文件。

### 脚注

```md
正文中的说明[^note]。

[^note]: 这是脚注内容。
```

### 数学公式

兼容旧 Hugo 的四组分隔符：`$$…$$`、`$…$`、`\(…\)`、`\[…\]`。
只有检测到公式的文章才会加载 KaTeX 资源。
当前实现使用 KaTeX 官方浏览器包与 auto-render 扩展，并附带 Subresource Integrity 校验；代码围栏和行内代码中的美元符号不会触发公式加载。
块级长公式在窄屏中可横向滚动，不会撑破正文栏。

```md
行内公式：$E = mc^2$

块级公式：
$$
\int_0^1 x^2 \, dx = \frac{1}{3}
$$
```

### 参考文献

本站采用便于个人写作维护的“简化 Chicago 作者—年份制”。文章结尾统一使用
`## 参考文献`；只有实际阅读、引用或据以陈述事实的材料才进入这一部分。仅供继续探索、
正文并未直接使用的资料另设 `## 延伸阅读`，不要混入参考文献。

正文中可以保留语义明确的行内链接；涉及书籍、论文或需要明确出处的观点时，推荐同时写出
“作者（年份）”或“（作者 年份）”。脚注主要用于补充解释，不重复承担完整书目信息。

参考文献使用无序列表，每条按“作者. 年份. 标题. 出版信息. 稳定链接”组织：

```md
## 参考文献

- 拉图尔，布鲁诺. 2022.《我们从未现代过：对称性人类学论集》. 刘鹏、安涅思译. 上海：上海文艺出版社.
- Gell, Alfred. 1998. *Art and Agency: An Anthropological Theory*. Oxford: Oxford University Press. https://doi.org/10.1093/oso/9780198280132.001.0001.
- OpenAI. 2026. “[Introducing GPT‑Live](https://openai.com/index/introducing-gpt-live/).” July 8, 2026.
```

维护时遵循以下规则：

1. 论文优先写完整 DOI 地址（`https://doi.org/...`），不要只写裸 DOI。
2. 书籍写明作者、年份、书名、译者（如有）、出版地和出版社；阅读札记优先记录实际阅读的版本。
3. 网页有作者和发布日期时照常记录；缺少日期时使用 `n.d.`，并补充访问日期。
4. 产品、API 与软件功能优先引用官方文档；新闻事实可引用署名清楚的报道。
5. 同一篇文章只保留一个 `## 参考文献`，旧有的“参考资料”“资料来源”等标题统一迁移到这里。

### 本地图片

可将需要随站点发布的图片放到 `public/images/`，在文章中使用：

```md
![图片说明](/images/example.png)
```

远程图片仍可使用，但站点可用性将依赖第三方图床。长期建议逐步迁移重要图片到
`public/images/`，并使用小写英文文件名。

## 旧主题样式的取舍

本次参考了以下旧主题文件：

- `custom.css`：保留并重写了提示框、响应式表格、图片集、键帽和脚注的设计意图。
- `style.css`：参考了正文、标题、代码块、表格和引用的基本排版。
- `style.css.bak`：仅作为历史参考，不作为迁移源，避免重复规则重新进入项目。

没有迁入旧主题的导航、归档、个人简介、notes grid、整页暗色反转以及远程字体声明。
这些规则与当前三栏目网站无关，而且整体搬入会增加样式覆盖和升级成本。

旧 Hugo `config.yaml` 无需修改：新站不会读取它。旧站仍可按原配置运行，新站的兼容逻辑
集中在 `scripts/markdown.mjs`，正文样式集中在 `public/styles.css`。

## 遇到未知格式时

1. 先运行 `npm test`。构建日志会指出所属文章和未兼容格式。
2. 检查生成页面中的“未兼容格式”提示，确认它原本在 Hugo 中的用途。
3. 在旧主题的 `layouts/shortcodes/`、`config.yaml` 和上述 CSS 中查找定义。
4. 将转换规则加入 `scripts/markdown.mjs`，样式加入 `public/styles.css`，并补充测试。

不要直接复制整个 Hugo 主题或在单篇文章中加入全局脚本。这样可以让格式扩展保持可测试、
可移除，也不会让内容文件与某个主题版本永久绑定。
