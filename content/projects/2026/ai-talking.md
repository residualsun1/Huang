> **一句话定位**：Her 是一个以图像记忆为入口的中文 AI 语音陪伴 Demo。用户上传一张照片，AI 将画面中的可见线索作为对话起点，随后通过文字或语音展开交流，并把这次交流保存为一段可以重新进入、聆听和回看的设备本地记忆。
>
> **我的角色**：独立发起并主导产品定义、需求拆解、交互设计、模型选择、迭代验收与上线；借助 Codex 完成技术调研、工程实现、测试与部署。
>
> **项目周期**：2026.07.15—2026.07.30，在两周窗口内用 8 个活跃开发日完成从想法、可交互 Demo 到公网部署；累计 56 次 Git 提交。
>
> **项目状态**：公开可体验的早期原型；React / TypeScript / WebGL / Qwen / IndexedDB / Cloudflare Workers。

## 先说结果

Her 最初看起来像一个“带粒子效果的聊天机器人”，但迭代后形成了一条更完整的产品闭环：

```text label="核心体验闭环"
上传照片
  → 将照片重构为可交互的粒子记忆
  → 云端图像理解（当前默认开启，可在设置中关闭）
  → 文字或语音对话
  → AI 语音回复
  → 将会话整理为记忆
  → 在回廊、卡片与日历中再次进入
```

当前版本已经：

- 跑通图片上传、多模态理解、中文对话、语音合成、会话总结与本地记忆保存；
- 使用 WebGL 粒子画面、声音响应和沉浸模式建立区别于普通聊天框的交互语言；
- 使用 Qwen 承担生产环境中的图片理解、对话、总结和语音合成，并保留无 API Key 也可运行的 Mock 模式；
- 将模型密钥隔离在服务端，记忆默认保存在用户设备的 IndexedDB 中，同时明确云端模型能力仍会产生数据传输；
- 部署到 Cloudflare Workers，并通过 GitHub 保留完整版本历史；
- 建立 3 组 smoke / contract tests，覆盖服务端渲染、Mock API 和关键产品交互契约。

## 项目缘起：我想解决的不是“怎么聊天”

项目受到 Spike Jonze 的电影 *Her*、博主「秒秒 Guo」的视觉实验，以及我自己使用语音模型的体验启发。在此前的[语音对话记录](/prompts/GPT-Live-Samantha/)中，我已经感受到：语音、停顿和上下文会让 AI 比纯文字更接近一种“在场的陪伴”。

但普通 AI 对话产品仍有三个问题：

1. **对话从空白输入框开始。** 用户需要先想清楚“我要说什么”，开口成本仍然很高。
2. **对话结束后只剩聊天记录。** 一段有意义的交流很快沉入时间线，缺少值得重新进入的载体。
3. **视觉与声音往往只是装饰。** 它们没有与用户正在谈论的对象、说话状态和记忆结果形成同一套体验。

因此，我提出了一个产品假设：

> 如果让一张照片成为用户和 AI 共同注意的对象，再让图像、语音与记忆保存共同参与交互，AI 陪伴就可能不只是“得到一句回复”，而是帮助用户重新接近一段经历。

这也让我把产品目标从“复现电影中的 Samantha”，逐渐收敛为一个更可验证的问题：**怎样让一次 AI 对话有具体的起点，并留下可回看的结果？**

## 产品定义：从照片开始，到记忆结束

### 目标用户与场景

以下定位来自个人观察、参考产品拆解与开发中的体验假设，尚未经过正式用户访谈验证。首版面向愿意借照片回看生活、又不一定知道该怎样开口的中文用户。典型场景不是高频办公，而是一个相对安静、低频但有情绪浓度的时刻：

> 当一张旧照片勾起某段经历时，我希望 AI 能从画面出发，用克制的方式陪我谈一会儿，并把这次交流整理成日后可以重新进入的记忆。

### 首版范围

我没有把 Her 直接设计成完整社交产品或“无所不能的 Agent”，而是将范围限制在一个单用户、可运行、可展示的 MVP：

| 首版要完成 | 首版明确不做 |
| --- | --- |
| 图片、文字和语音构成一次完整会话 | 账号、社交关系与公开社区 |
| 会话可被总结、保存、重看和删除 | 云端同步与跨设备协作 |
| 真模型与离线 Mock 都能运行 | 自主执行外部任务的通用 Agent |
| 用户可在设置中关闭图片理解 | 心理诊断、治疗或真实情绪判定 |

早期我曾把它称为 Agent。随着实现深入，我意识到它目前更准确的定义是：**一个具备多模态理解、语音交互和本地记忆闭环的 AI 产品 Demo**。这次概念修正也帮助我避免为了“Agent”标签加入与核心体验无关的复杂度。

### 五条设计原则

我用以下原则审视需求与实现，其中“主动授权”仍是当前版本没有完全达到、需要优先修正的一项：

1. **记忆优先于聊天。** 聊天是过程，照片与保存后的记忆才是用户反复进入的对象。
2. **氛围服务于内容。** 粒子、音乐和动效必须回应图像与声音，不能遮挡主体或拖慢关键操作。
3. **AI 的判断必须可被纠正。** 模型只能提出低置信度的氛围假设，用户的自述永远优先。
4. **让数据边界可理解、可控制。** 用户应当清楚什么内容只保存在设备、什么内容会发送给云端模型，并能在发送前主动决定。当前版本可以关闭图像理解，但默认仍为开启，尚未做到逐次主动授权。
5. **先闭环，再加功能。** 每一个新增功能都要回答：它是否让“照片—对话—记忆”的闭环更完整？

## 核心体验

### 1. 把照片变成可进入的“记忆对象”

用户上传照片后，系统会把图像重构为高密度、可交互的 WebGL 粒子画面。粒子会响应鼠标、拖拽、语音能量和背景音乐；用户也可以缩放画面或隐藏界面，只保留粒子图像。

默认上限为 262,144 个粒子，并会根据设备内存、CPU、屏幕和 `reduced-motion` 设置降到 131,072 或 65,536。这个自适应不是为了展示一个更大的数字，而是避免把“沉浸感”建立在只有高性能电脑才能运行的前提上。

这里最重要的并不是“粒子越多越好”，而是同时满足两个相互拉扯的目标：

- 主体需要保持可辨认，否则照片失去记忆锚点；
- 边缘需要有自然的溶解、流动和呼吸感，否则效果只是套在原图上的滤镜。

保存后的照片会进入“记忆”画廊。画廊最终取消了卡片边框，改为漂浮在黑色空间中的粒子对象，支持滚轮、拖动和点击进入，让用户感到自己是在浏览一组记忆，而不是翻阅普通后台卡片。

### 2. 让 AI 从“看见什么”开始，而不是猜测用户

当前版本的图像理解默认开启，用户可以在设置中关闭。启用时，浏览器会通过 Cloudflare Worker 将图片内容发送给 Qwen；原始图片则同时保存在设备本地，用于之后恢复记忆。设置文案曾写“发送压缩副本”，但当前实现只是对符合大小限制的原文件编码后发送，并没有真正进行重采样压缩——这是在代码核对中发现、需要修正的产品与实现偏差。

图片理解结果被拆成几类结构化信息：

- 画面中可以直接观察到的对象与关系；
- 可能的氛围线索及其依据；
- 对这一判断的置信度；
- 一个从画面自然引出、但不替用户下结论的问题。

这套设计刻意避免通过人物外观推断用户的真实情绪、身份、健康或敏感属性。例如，AI 可以说“冷色和空旷构图让我联想到安静”，但不能说“你当时一定很孤独”。如果用户回答“其实那天我很轻松”，后续对话必须以用户的解释为准。

对我而言，这不仅是提示词优化，也是一个 AI 产品判断：**模型的“会看图”不等于产品有权替用户解释记忆。**

### 3. 把语音做成一条完整链路

用户可以输入文字，也可以通过浏览器语音识别完成中文转写。AI 的回复由 `qwen-audio-3.0-tts-plus` 合成为语音，前端使用真实音频能量驱动波形和粒子，而不是用随机动画假装“正在发声”。

语音被拆成独立能力，而不是和聊天模型绑定：

- 浏览器语音识别负责将用户声音转成文字；
- 对话模型负责理解上下文和组织回复；
- TTS 模型负责音色、语速和表达风格；
- 播放层负责流式接收、缓存、波形与被打断后的状态恢复。

这种拆分让我可以单独调整语言能力、声音体验和播放性能，也避免用户切换文本模型时，音色被意外改变。

### 4. 让对话成为可以回看的结果

点击“留住记忆”后，系统会根据会话生成标题、摘要和整理后的正文，并保存：

- 原始照片与粒子展示；
- 用户和 AI 的逐轮文本；
- 时间戳与会话时长；
- 在设置中启用的用户原声保存（当前默认开启）；
- 图片理解上下文与记忆摘要。

保存顺序也经过了刻意设计：系统先把原始对话写入本地草稿，再请求 AI 总结；如果总结模型失败，草稿会标记失败状态，但用户已经说出的内容不会一起丢失。对这类产品而言，AI 生成内容可以失败，用户的原始表达不能随之消失。

用户可以在回廊中阅读记忆卡片、重放语音、删除内容，也可以把记忆固定到当天的日历。当前记忆数据默认保存在浏览器 IndexedDB 中，不会自动上传或跨设备同步。这里的“本地记忆”不等于“完全离线”：图片理解、对话、总结和 TTS 启用时，相应内容仍会经过服务端发送给云端模型。

这一选择同时服务了三个目标：降低首版工程范围、减少敏感记忆的云端暴露，并让没有账号系统的 Demo 仍然拥有真正可恢复的状态。

这里的“记忆”也只是设备本地的情节档案，并不是具备语义检索、用户画像和跨会话召回能力的 Agent 长期记忆；再次打开照片时，产品会基于图片上下文开启一段新对话。

### 5. 用音乐构成环境，而不是增加一个播放器

用户可以添加 `.mp3` 或 `.flac`，在可展开的音乐列表中切换；音乐只在当前页面使用，不上传、不持久化。频谱中的低、中、高频会分别影响粒子位移、光晕和闪烁，使背景音乐真正进入视觉系统。

产品内置一首默认背景音乐，但遵循浏览器规则，不会在用户未操作时自动播放。这样既保留氛围，也避免把声音变成打扰。

## AI 与工程架构

我将前端交互、服务端能力、模型适配和本地记忆拆成四层：

```text label="产品与模型架构"
浏览器
├─ React：页面、状态与语音交互
├─ WebGL / React Three Fiber：粒子记忆
├─ Web Audio：音乐与语音能量分析
└─ IndexedDB：本地记忆、图片与可选录音
             ↓
Cloudflare Worker API
├─ /api/image-context：图片理解
├─ /api/chat：流式对话
├─ /api/summary：记忆整理
└─ /api/tts/synthesize：流式语音合成
             ↓
Provider 适配层
├─ Live：生产环境真实模型
└─ Mock：无密钥、可重复的离线演示
```

生产链路当前使用 Qwen 完成图片理解、对话、总结与 TTS，语音识别则依赖浏览器 `SpeechRecognition`。代码中已经为 Qwen、DeepSeek、OpenAI、Anthropic 和 Gemini 建立文本能力适配层，但并不意味着五家模型都经过了生产验证。这样拆分不是为了在页面上堆模型名称，而是为了让“能力契约”与具体供应商解耦。

几项关键工程边界包括：

- API Key 只由服务端环境变量读取，不返回浏览器；
- 图片、对话和语音请求都有输入大小、长度与上游超时限制；
- 真模型不可用时显示明确的降级信息，不把本地 Mock 伪装成调用成功；
- Mock 模式不需要 API Key，方便开发、演示和自动化测试；
- 记忆、图片和开启保存后的录音留在设备中，清除网站数据时也会被一并清除；
- 当前图像理解与原声保存都默认为开启，数据说明和主动同意流程仍需补齐。

## 评测：区分“做出来”与“被验证”

目前的评测以工程验证和形成性体验测试为主，还不能等同于正式用户研究。为了不把主观满意包装成产品结论，我把已有证据与缺口放在同一张表里：

| 要验证的问题 | 当前方法与证据 | 仍然缺少 |
| --- | --- | --- |
| 核心闭环能否跑通 | lint、类型检查、生产构建通过；服务端渲染、Mock API、关键交互契约 3 组 smoke / contract tests；线上冒烟验证 | 浏览器端 E2E、多设备、弱网与长会话稳定性测试 |
| 图片理解是否克制 | 使用风景、人物和情绪不明确图片测试；加入“可见事实—氛围假设—依据—置信度—问题”结构；验证用户否认后模型会修正 | 固定测试集、评分 Rubric 与多人一致性评审 |
| 语音是否比系统朗读自然 | 从浏览器 `speechSynthesis` 迁移至 Qwen TTS，真实检查 WAV、播放链路和连续多轮录音 | 目标用户盲听、音色偏好与中断率 |
| 粒子效果是否兼顾辨识与氛围 | 对参考视频逐帧拆解，使用同图、固定音频反复对照；对失败版本执行回退 | 不同设备 FPS、GPU 占用和视觉可读性量表 |
| 服务是否足以公开展示 | GitHub 版本管理、Cloudflare 自动构建、密钥隔离、限频与错误边界 | 真实访问量、成本、完成率与留存数据 |

一次开发环境联调中，图片理解约 7.8 秒、连续对话约 1.9 秒、记忆摘要约 1.4 秒，短语音合成约 1.5 秒。这些数字只用于发现体验瓶颈，**不是稳定 SLA，也不是规模化性能结论**。后续如果继续投入，我会优先建立可重复的评测集，而不是继续凭感觉调模型。

## 关键迭代：产品不是一次写对的

### 迭代一：从静态参考图到可验收的交互状态

最初需求大量来自图片，但静态图无法说明粒子速度、回弹、声音映射和页面转场。我随后整理 9 张研究图片与 8 段参考视频，并把视觉拆成待机、聆听、思考、回复、保存和回廊六类状态。

这一过程让我意识到：参考资料不是“做成这种感觉”就结束了，还需要转译成可观察的验收条件。例如，同一张图片在静止、鼠标经过、拖拽和强音频下分别应发生什么，才是开发可以执行的需求。

### 迭代二：在“看得清”与“有粒子感”之间反复校准

粒子视觉经历过几次明显失败：

- 粒子过强，主体只剩光点；
- 为了保真加入清晰底图，拖动时却暴露出“底图 + 特效层”的割裂；
- 把已经粒子化的参考图再次处理，造成双重粒子化；
- 为追求上缘羽流加入触须式扩散，反而侵蚀主体；
- 某次着色器变量被误删，导致整张图不显示。

最终方案不再依赖固定底图，而是让高密度粒子共同构成有厚度的图像表面：主体区域更稳定，轮廓与外围承担扩散，音乐只让主体轻微呼吸。更重要的是，当后续实验明显变差时，我选择回到已经验证过的提交，而不是为了证明新方案正确继续堆补丁。

### 迭代三：从卡片列表改成真正的记忆画廊

第一版回廊本质仍是横向卡片，拖动、滚轮、点击与删除之间经常争抢事件。改成无边框粒子画廊后，又先后出现“点击无法进入”“删除被父级吞掉”“滚轮切换卡顿”等问题。

解决方案不是继续调动画速度，而是重新划分手势职责：

- 拖动画廊空白区域才移动画廊；
- 拖动粒子对象只影响粒子；
- 移动超过阈值才进入拖拽模式；
- 删除按钮使用独立点击层和更大的触摸热区；
- 同时运行的实时粒子画布受控，其余记忆使用轻量预览。

这次迭代让我理解：所谓“丝滑”不只是帧率，也来自用户操作意图不会被系统误判。

### 迭代四：主动删除“看起来很 AI”的功能

早期版本包含多个 AI 角色彼此对谈的 `AI Salon`，也保留了英文回复和点击翻译。它们视觉上有趣，却没有强化目标用户的核心任务，还增加了页面、接口、数据结构和维护成本。

在明确中文用户和“照片—对话—记忆”主线后，我删除了 AI Salon、翻译 API 与相关模型能力，把导航收敛为“记忆 / 回廊 / 音乐”，并将对话改为中文优先。

这次删除比增加功能更能说明产品方向：**创新感不能成为保留低价值功能的理由。**

### 迭代五：从“能出声”到连续多轮可用

最初使用浏览器系统朗读，虽然成本低，但音色机械、不同设备差异很大。接入 Qwen TTS 后，又遇到临时音频域名、HTTPS、浏览器自动播放和录音后扬声器无法恢复等问题。

连续语音失败的根因最终不是模型没有返回，而是浏览器在录音结束后仍占用音频会话，错过了恢复扬声器的用户手势窗口。修复后的顺序变成“停止录音—释放麦克风—恢复扬声器—提交对话—播放回复”，并加入流式 PCM 播放、缓存和本地语音兜底。

它提醒我，AI 产品的体验瓶颈常常不在模型本身，而在模型之前和之后的完整链路。

## 我如何与 AI 协作

这个项目不是“输入一句 Prompt，AI 自动生成一个网站”。我把 Codex 当作研究、工程与验证协作者，而不是替代产品判断的一键工具。

我的主要职责是：

- 提出产品问题，补充图片、视频和体验参照；
- 界定目标用户、MVP 范围、优先级与非目标；
- 把“感觉不对”逐步澄清为可观察的交互差异；
- 验收每一版，拒绝、回退或删除偏离主线的方案；
- 决定模型、隐私边界、上线方式与最终取舍。

AI 主要帮助我：

- 把自然语言需求转成产品状态、技术方案与测试条件；
- 调研模型、浏览器能力、WebGL 方案和部署约束；
- 实现代码、定位日志、补充测试并维护文档；
- 将每轮修改保存为 Git 提交，完成构建和部署验证。

```text label="人机协作循环"
提出问题与参考
  → 拆成可验收标准
  → AI 协助实现
  → 构建、测试与线上验证
  → 我进行体验验收
  → 保留、修正、删除或回退
  → 进入下一轮
```

56 次提交记录了这条过程。对我最重要的学习是：高质量 AI 协作不只依赖“写清 Prompt”，还依赖目标定义、上下文管理、验收标准、风险边界和停止继续加功能的判断。

## 当前结果、限制与下一步

Her 已经证明我可以把一个模糊的体验想法，逐步拆成产品范围、AI 能力、交互状态、数据结构、评测方法和可公开访问的 Demo。但它仍然是产品实验，不是经过市场验证的成熟产品。

回看提交记录，我在早期把大量迭代投入了粒子视觉。它帮助产品建立辨识度，也让我学会把感性参考转译成可执行参数；但在没有用户验证前，这同样属于偏早的体验优化。所以下一阶段的优先级不会是再增加一种粒子形态，而是先补授权、评测和用户证据。

当前限制包括：

- 尚未对目标用户开展正式访谈、可用性测试或留存观察，不能声称解决了真实市场需求；
- 图像理解和原声保存当前默认为开启，逐次主动授权、数据说明与图片压缩实现仍需优先补齐；
- 浏览器语音识别的可用性依赖设备和浏览器，移动端与弱网仍需系统测试；
- 本地记忆不会跨设备同步，清除网站数据也会清除内容；
- 缺少面向陪伴类产品的完整安全机制，例如危机情境处理、依赖风险与模型输出治理；
- 现有测试以构建、接口与源码契约为主，尚无浏览器 E2E、视觉回归和系统化 AI Eval；
- 还没有埋点，因此不能提供转化率、保存率、复访率等业务指标。

下一阶段我会优先补“验证”，而不是继续扩功能：

1. 将图像理解与原声保存改为清晰的主动授权，补齐数据去向说明与真实图片压缩；
2. 邀请 5—8 位目标用户完成“上传—对话—保存—再次进入—删除”的任务测试；
3. 记录首轮对话完成率、首次回复等待、记忆保存率、误触点与主动退出原因；
4. 建立图片理解、对话、摘要与安全评测集，检查事实准确、过度推断、可纠正性与问题质量；
5. 对桌面和移动设备记录 FPS、首屏耗时、首字 / 首段语音等待、失败率和无障碍问题；
6. 只有在用户确实需要跨设备回看时，再评估账号、加密同步与云端成本。

## 我从 Her 学到什么

Her 最有价值的部分不是“我调用了几个模型”，而是我完成了几次思维转换：

- 从“做一个像 *Her* 的 AI”转向“定义一个具体、可验证的陪伴场景”；
- 从“功能越多越完整”转向“围绕核心闭环主动删减”；
- 从“模型能生成答案”转向“关注授权、纠错、延迟、播放和保存的全链路体验”；
- 从“感觉更好看”转向“用参考、状态、测试和回退记录支撑判断”；
- 从“让 AI 帮我写代码”转向“组织人与 AI 的分工、上下文、验收与版本管理”。

我目前把 Her 看作一项仍在继续的产品实验：它没有证明 AI 已经能够理解人的记忆，却让我更具体地理解了，**AI 产品经理的工作不是把模型能力摆到界面上，而是决定模型在什么时刻介入、知道什么、不应判断什么，以及怎样让一次交互留下真实价值。**
