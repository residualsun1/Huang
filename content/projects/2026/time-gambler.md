> **一句话定位**：Time Gambler 是一个把 AI 任务拆解、完成验证与链上质押连接起来的效率产品 Demo。用户先为目标设定期限并押下注金，AI 再协助把模糊目标拆成行动步骤，并根据文字、图片或测验判断任务是否完成，最后由智能合约记录结果。
>
> **我的角色**：四人团队中的产品设计与路演主力。我组织讨论、推动产品理念收敛，持续提出信息架构与 UI 迭代意见，梳理路演叙事并完成现场展示；同时参与 AI Agent 链路调试。前端、合约与大部分 Agent 代码主要由队友借助 AI 完成，我不是项目的主要代码实现者。
>
> **项目周期**：2026.01.27—2026.02.01，在五天集中开发窗口内完成从产品构想、可交互 Demo 到路演交付；参加 ETHPanda × LXDAO Web3 实习计划的 SPARK AI Hackathon，并获得亚军。
>
> **项目状态**：公开可访问的黑客松原型；React Native / Expo / FastAPI / SpoonOS / Solidity / Foundry。Web 前端可以体验，核心链上闭环仍以赛时 Demo 与本地开发环境为主。

## 先说结果

Time Gambler 是我第一次参加黑客松，也是我第一次在团队项目中集中承担产品设计、协作推进与公开表达。五天里，我们把一个抽象问题——“为什么知道该做什么，却迟迟无法行动”——收敛成了一条可以被演示的产品闭环：

```text label="核心产品闭环"
输入一个模糊目标
  → AI 拆成可执行步骤
  → 选择期限并提交链上质押
  → 在期限内执行任务
  → 提交文字、图片或测验结果
  → AI 给出结构化判断
  → 合约记录成功、失败或超时
  → 退回质押，或按规则完成结算
```

在这个过程中，团队完成了：

- 从“普通待办工具”中切出一个更明确的产品假设：用真实后果提高用户对承诺的重视程度；
- 用两个边界清楚的 AI 任务连接行动前后：开始前负责拆解，结束后负责验证；
- 用智能合约保存任务、期限、质押与结果状态，形成一条可运行的 Demo 链路；
- 完成创建任务、AI 分析、提交证明、验证结果、任务看板与 AI 陪伴角色等主要界面；
- 在四分钟路演中讲清问题、定位、核心机制、技术结构与未来设想，并获得赛事亚军。

## 项目缘起：我们想解决的不是“缺少一个待办清单”

我们观察到一种常见矛盾：学习资料和效率工具越来越多，但“知道”并没有自然转化成“行动”。拖延、疲惫、注意力分散与过多选择，常常让人停留在计划、收藏和反复准备中。

市面上的待办、番茄钟和习惯打卡产品已经能够记录任务，却很难回答另一个问题：

> 当用户已经知道自己应该做什么，却仍然没有开始时，产品还能提供什么不同的推动力？

我们的答案不是继续增加课程、社区、排行榜或复杂的任务管理能力，而是做减法，只保留三个关键动作：

1. **让目标变得具体。** AI 把“我要学习 Python”一类宽泛目标拆成可执行步骤。
2. **让承诺产生后果。** 用户主动设定期限与质押，使任务不再只是一条可以随时划掉的文字。
3. **让结果得到反馈。** AI 根据用户提交的证据进行验证，合约再执行确定性的状态变化。

这形成了 Time Gambler 的核心产品理念：**用户不一定需要无限增加方法，也可能需要一个帮助自己停止观望、立刻行动的开关。**

## 产品定义：为主动选择强约束的人设计

### 目标用户与场景

首版面向的不是所有效率工具用户，更不是需要医学干预的人群。我们设想的用户是：已经有明确改变意愿，却容易在启动阶段拖延、在执行中分心，并且愿意主动接受更强外部约束的人。

典型场景是一个边界清楚、可以在短时间内验证的任务：

> 我今晚想完成一章课程或一组练习，但过去经常把计划拖到第二天；我愿意先设定期限和可承受的质押，再让 AI 帮我拆解步骤并在结束后检查成果。

“ADHD”出现在仓库名称和赛时叙事中，但当前 Demo 没有开展临床研究，也不具备诊断或治疗能力。因此更准确的产品表述是：**一次关于启动困难、注意力分散与外部承诺机制的产品实验**，而不是 ADHD 行为矫正工具。

### 黑客松 MVP 的范围

五天时间不足以验证一个完整商业模式。我们将 MVP 收敛在“创建承诺—执行—提交证据—获得结果”这一条主链路上：

| Demo 已完成 | 尚未被证明或完整实现 |
| --- | --- |
| AI 将模糊目标拆成步骤与时间建议 | 任务拆解是否能长期提高行动率 |
| 为任务设置期限、质押并写入合约 | 主网资金安全与可持续经济模型 |
| 通过文字、图片或测验提交结果 | AI 验证的准确率、公平性与抗作弊能力 |
| 合约保存任务状态并按成功、失败或超时处理 | 生产级 Oracle、密钥管理与申诉机制 |
| 任务看板、状态反馈和 AI 陪伴角色 | 长期个性化监督、第三方对赌与社交玩法 |

这一划分是我现在重新审视项目后补上的。赛时材料更强调愿景与冲击力，而作品集需要清楚回答：**当时真正做出了什么，什么仍然只是产品假设。**

### 四条产品原则

1. **做减法，而不是再造一个复杂效率平台。** 每项功能都必须直接服务“开始—执行—验证”的闭环。
2. **质押必须由用户主动选择。** 强约束不应变成诱导，金额、风险与退出边界需要清楚可见。
3. **AI 处理模糊性，合约处理确定性。** AI 可以拆解目标、理解证据，但最终状态与资金规则应由可检查的程序执行。
4. **验证结果必须可解释、可质疑。** “AI 说你失败了”不能成为不可申诉的最终答案。

## 核心体验：两个 Agent 任务，一条承诺闭环

### 1. 开始前：把“我想做”变成“下一步做什么”

用户输入目标后，任务拆解 Agent 会生成若干子任务、预计时间与执行建议。它解决的不是知识问答，而是降低启动成本：用户不必先完成一轮复杂规划，便能看到第一步。

代码中的拆解结果使用结构化字段返回，前端再把它呈现为行动建议；当模型不可用时，系统还保留基础降级结果，保证黑客松演示不会完全中断。

这让我第一次具体理解到，AI 产品中的“智能”不只来自模型生成了多少内容，还来自输入、输出和下一步操作能否接得上。对 Time Gambler 而言，好的拆解不是写得更丰富，而是让用户更容易开始。

### 2. 创建承诺：把期限与质押写进任务

用户确认目标后，可以选择期限与质押金额并创建链上任务。合约记录任务所有者、描述、金额、截止时间和状态：

- 验证通过后，任务进入成功状态，用户可以取回质押；
- 验证失败或超过期限后，任务进入失败或结算流程；
- 当前合约把未退回部分按规则分配到平台金库与奖励池。

链上机制的价值不只是“使用了 Web3”，而是让承诺规则在任务开始后不被随意修改。但这同时引入资金风险、交易成本和用户焦虑，因此它只能被视为待验证的产品假设，不能因为技术上可实现就默认对用户有益。

### 3. 结束后：让 AI 判断“证据是否与目标相关”

用户可以提交文字说明、图片证据，或完成 AI 根据任务生成的选择题。验证 Agent 会结合原任务与提交内容，返回：

- 是否通过；
- 判断理由；
- 0—100 的评分；
- 供后续状态更新使用的结构化结果。

路演中，我们把这部分概括为 Graph Workflow：不同证明方式经过分析后汇合成可供合约使用的布尔结果。实际仓库当前主要通过 FastAPI 与 Verify Agent 的多个接口实现，再由前端发起链上状态更新。

这种设计让 Demo 能够跑通，却也暴露了 AI 产品的核心难题：**证据相关不等于任务真实完成，模型给出高分也不等于判断客观。** 如果产品继续发展，就必须加入固定评测集、规则透明度、人工申诉与异常处理，而不是直接把模型输出当作事实。

### 4. 用状态与陪伴角色补全反馈

任务看板展示进行中、已完成和全部任务；创建、等待验证、通过与失败也有对应反馈。右侧 AI 角色用更具情绪张力的语言提醒用户下注或提交证明，试图让产品从冷冰冰的合约工具变成一个始终在场的“数字监督者”。

这个角色在黑客松展示中帮助产品建立了记忆点，但它目前主要承担文案与氛围功能，还不是基于长期行为数据工作的个性化 Agent。赛时提出的“从数字监督者成长为赛博伙伴”属于后续愿景，而不是当前能力。

## AI 与链上架构：让不同系统承担不同责任

```text label="Demo 架构"
React Native / Expo 前端
├─ 创建目标、期限与质押
├─ 展示 AI 拆解结果
├─ 提交文字、图片或测验
└─ 展示任务与验证状态

FastAPI + SpoonOS
├─ Breakdown Agent：目标 → 子任务与时间建议
├─ Verify Agent：目标 + 证据 → 通过 / 理由 / 评分
└─ Quiz：生成题目并评分

Solidity 合约
├─ 保存任务、期限、质押与状态
├─ 限制验证者权限
└─ 处理退款、失败与超时结算
```

对 AI 产品经理而言，这套结构最值得学习的不是技术名词，而是责任边界：

- **模型擅长处理非结构化输入。** 它可以理解自然语言目标、图片和证明文本。
- **接口负责把不确定输出变成产品可用的格式。** 前端需要的是稳定字段，而不是一段无法执行的自由回答。
- **合约擅长执行确定规则。** 它不判断一张图片意味着什么，只接收验证结果并改变状态。
- **产品必须处理系统之间的缝隙。** 模型超时、解析失败、链上交易失败、前端本地状态与合约状态不一致，都会破坏完整体验。

当前实现仍带有明显的黑客松特征：AI 服务会提供演示降级逻辑，链上验证由客户端继续提交，公开页面与本地链环境并非完整的生产部署。这些做法有助于五天内交付 Demo，但不能直接用于真实资金场景。

## 我的职责：主导产品收敛，而不是把团队代码写成个人成果

这是一个团队项目，我希望作品集既呈现自己的贡献，也尊重队友的技术工作：

| 工作部分 | 我的实际参与 | 团队边界 |
| --- | --- | --- |
| 问题与定位 | 组织会议讨论，推动团队从宽泛的效率工具收敛到“AI 拆解 + AI 验证 + 质押后果” | 产品方向由四人共同讨论形成 |
| 产品理念 | 提出并反复强化“做减法”“立刻行动”和强约束体验，梳理目标用户与表达方式 | 机制可行性由产品与技术共同判断 |
| 信息架构与 UI | 根据核心流程持续提出页面层级、状态反馈、视觉与文案调整，并参与验收 | 前端代码主要由队友借助 AI 实现 |
| AI Agent | 参与拆解与验证链路的联调、观察异常结果并协助定位问题 | Agent 主体代码并非由我独立完成 |
| 智能合约 | 参与讨论它在产品闭环中的作用 | 合约设计、实现与测试主要由队友负责 |
| 路演与宣发 | 梳理四分钟叙事、制作和修改演示材料，负责最终现场讲解 | 团队共同提供技术内容与 Demo 支持 |

这次分工让我理解：产品角色的价值不一定体现在提交了最多代码，而在于能否让不同成员围绕同一个用户问题工作，把讨论变成范围、流程、界面、验收标准与可讲清楚的结果。

## 关键迭代：五天里真正发生了哪些产品判断

### 迭代一：从“功能更多”转向“后果更明确”

早期讨论很容易滑向一个功能齐全的效率平台：任务、计时、打卡、社区、奖励都可以加入。但同类产品已经很多，五天也不可能完成完整平台。

我们最终用“减法”重新判断优先级：任务管理只是载体，真正需要被验证的是，**当承诺带有主动选择的后果时，用户是否更愿意开始并完成任务。** 这让质押、期限与验证成为主链路，其余能力退到后面。

### 迭代二：把泛化的“AI 监督”拆成两个具体岗位

“让 AI 监督用户”听起来像一个概念，却无法直接变成界面。我们把它拆成两个发生在不同时间点的任务：

- 行动前，AI 是规划者，负责把模糊目标变成下一步；
- 行动后，AI 是验证者，负责判断提交内容是否与原目标相关。

这个拆分同时帮助产品与技术对齐：团队能够为每个 Agent 定义输入、输出和失败状态，路演也能用一条前后呼应的流程说明 AI 为什么存在。

### 迭代三：从页面拼接转向状态完整

一条黑客松 Demo 不只是需要几张漂亮页面，还需要观众看懂任务怎样从创建变成成功或失败。因此 UI 迭代逐渐围绕状态展开：空任务、填写目标、AI 分析、确认质押、等待完成、提交证据、验证成功和验证失败。

我在这一阶段频繁提出界面层级、状态反馈和视觉表达上的修改。对我而言，这也是第一次把“这里不好看”逐步转成更具体的问题：当前页面最重要的信息是什么、用户接下来应该点哪里、状态改变是否能被立即看见。

### 迭代四：从介绍技术转向讲清人的选择

路演最初很容易堆叠 Web3、SpoonOS、ReAct Agent、Graph Agent 与智能合约。但四分钟内，听众首先需要理解的不是技术栈，而是用户为什么愿意使用它。

最终叙事从“这是一个用了哪些技术的项目”，调整为：

```text label="四分钟路演叙事"
资源越来越多，但行动仍然困难
  → 普通工具缺少真正的约束
  → Time Gambler 让用户为当下主动下注
  → AI 帮助开始，也负责检查结果
  → 合约让承诺产生确定后果
  → Demo 展示完整流程
  → 最后再说明技术结构与未来愿景
```

这次路演让我第一次感受到，产品表达不是开发完成后的包装，而是对产品逻辑的再次检验：如果一句话讲不清用户、问题和机制，往往说明产品本身还没有收敛。

## 产品评测：亚军是结果，不是用户验证

目前能够确认的证据主要来自工程实现、团队演练与赛事评审，还没有正式用户研究：

| 要验证的问题 | 当前证据 | 仍然缺少 |
| --- | --- | --- |
| 核心流程能否被演示 | 前端、AI 接口与合约代码形成完整结构；公开 Web 页面可访问；赛时完成现场 Demo | 公开环境的稳定端到端链路、移动端与弱网测试 |
| 合约状态是否按规则变化 | Foundry 测试覆盖任务创建、验证、退款与超时结算等主要路径 | 安全审计、主网风险评估与生产级 Oracle |
| 产品是否容易被理解 | 团队多轮路演排练，并在赛事评审中获得亚军 | 独立用户的任务成功率、理解偏差与可用性观察 |
| AI 拆解是否真正帮助开始 | Prompt 与结构化输出可以生成可执行步骤 | 固定任务集、人工评分 Rubric、用户采纳与修改比例 |
| AI 验证是否可信 | 支持文字、图片和测验，返回理由与评分 | 准确率、误判率、抗作弊测试、申诉与人工复核 |
| 质押是否改善完成率 | 产品机制与链上结算已经被表达和实现 | 对照实验、长期完成率、焦虑感与后悔程度 |

如果继续推进，我不会先扩展更多玩法，而会邀请 5—8 位目标用户完成一次从目标输入到证明提交的任务测试，并记录：

- 从输入目标到成功创建任务的完成率与放弃点；
- AI 拆解建议被直接接受、修改或忽略的比例；
- 用户能否理解质押后果，以及金额选择是否产生压力；
- 证明提交完成率，以及用户与 AI 对验证结果的分歧；
- 在无质押、模拟质押与小额质押条件下，完成率是否真的变化；
- 用户对产品的信任、焦虑、后悔与再次使用意愿。

只有这些证据出现后，我们才能判断“强约束是否有效”，而不是用获奖或模型评分替代产品验证。

## 我如何理解团队中的 AI 协作

这个项目的大部分代码由队友通过 Vibe Coding 快速实现。我参与的重点不是把这些代码算作自己的成果，而是观察和推动“产品意图怎样经过人和 AI 变成可用 Demo”。

我学到的第一件事是：AI 可以大幅加快搭建速度，却不会自动保证团队对产品的理解一致。一个成员修改 Prompt、一个成员调整页面、另一个成员改变合约字段，如果缺少共同的流程和验收标准，局部都能运行，整体仍可能断裂。

我在协作中主要做了三类工作：

- **补充上下文。** 向团队说明目标用户、核心理念、路演场景和页面优先级，避免 AI 只根据局部代码扩展功能。
- **用完整流程验收。** 不只检查接口是否返回，而是从输入目标开始，确认拆解、质押、证明、判断和状态反馈能否连续发生。
- **把异常转回产品问题。** 当 Agent 输出过于笼统、证明判断与任务不相关或页面状态不一致时，先判断需要修改 Prompt、结构化字段、交互提示还是系统边界。

这让我认识到，AI 产品协作的关键不只是“谁更会写 Prompt”，还包括问题定义、上下文同步、接口契约、结果评测、版本边界与最终责任。Vibe Coding 缩短了从想法到 Demo 的时间，也放大了产品验收的重要性。

## 重新审视：当前版本最需要正视的风险

### 1. 强约束并不天然等于好产品

质押利用的是用户对损失的敏感，但它也可能加重焦虑、冲动下注或事后后悔。正式产品应该先使用模拟积分或测试币验证机制，设置清晰上限、冷静期和风险提示，并允许用户选择更温和的承诺方式。

### 2. AI 验证不是客观裁判

文字和图片可以被伪造，同一份证据也可能得到不同判断。当前评分更适合作为 Demo 反馈，不应直接决定真实资金。下一版需要固定评测集、清楚的通过规则、置信度、人工复核与申诉入口。

### 3. 证据会带来隐私责任

图片证明可能包含书桌、住址、聊天记录或个人身份信息。当前后端会把上传文件写入服务端目录，尚未完成自动删除与完整的数据生命周期设计，因此不能宣称“阅后即焚”，也不应鼓励用户提交敏感图片。

### 4. Demo 架构不能直接承载真实资金

当前 Oracle、客户端提交、密钥管理、降级逻辑与本地链配置都服务于黑客松演示。上线真实资金前需要重做权限、签名、审计、异常恢复、监控与公开环境部署，而不是简单切换一个合约地址。

### 5. 产品定位必须远离医疗承诺

拖延、分心与启动困难可能来自很多原因。没有临床证据时，产品只能描述具体行为场景，不能声称矫正 ADHD、重塑多巴胺或提供治疗效果。

这些限制不会否定黑客松成果。相反，能够在赛后从兴奋的愿景退回实现与证据，是我从“做出一个吸引人的 Demo”走向“理解 AI 产品责任”的重要一步。

## 当前限制与下一步

Time Gambler 已经完成一次紧凑的 0→1：团队在五天内提出问题、选择机制、搭建前后端与合约、完成界面、组织路演并交付结果。但它仍然是早期原型：

- 没有正式用户访谈、可用性测试、行为数据或留存数据；
- 没有证明质押比普通提醒更有效，也没有验证它对不同用户的心理影响；
- AI 拆解与验证缺少系统化 Eval、人工基线和申诉流程；
- 公开页面还不是稳定的生产级链上应用；
- 资金安全、Oracle、隐私、数据删除与模型失败处理仍需重构；
- 长期个性化、第三方对赌和商业模式仍是愿景，而非已交付能力。

如果继续投入，我会按以下顺序推进：

1. 先把真实资金改成模拟承诺，完成 5—8 位目标用户的可用性测试；
2. 建立拆解与验证评测集，记录相关性、可执行性、误判率和人机分歧；
3. 根据测试结果重写目标用户、使用边界与风险提示；
4. 补齐证明数据的授权、保存、删除与敏感内容规则；
5. 在独立审计、生产级 Oracle 和异常恢复完成前，不接入真实资金；
6. 只有核心闭环得到验证后，再讨论长期陪伴、第三方挑战与商业模式。

## 我从 Time Gambler 学到什么

这个项目对我的意义，不是把一次黑客松经历包装成成熟商业产品，而是记录我第一次走进产品设计与团队交付的过程：

- 我第一次组织多人讨论，并尝试让不同技术背景的成员围绕同一个产品问题收敛；
- 我第一次把抽象理念拆成目标用户、核心流程、界面状态与四分钟叙事；
- 我第一次意识到，AI Agent 不是一个标签，而是一组需要定义输入、输出、失败状态与评测方法的产品能力；
- 我第一次在没有主导代码的情况下理解自己的责任：推动决策、同步上下文、持续验收，并如实说明贡献边界；
- 我第一次经历从“觉得功能很酷”到“追问它是否安全、可信、可验证”的思维变化；
- 我也第一次看到，公开表达可以反过来迫使产品变得更清楚。

获得亚军给了团队正向反馈，但我更珍视五天里形成的工作方法：**先定义一个值得解决的问题，再把它收敛成能够运行、能够验证、也能够诚实解释边界的产品。**

对当时的我而言，Time Gambler 是一次从 0 到 1 的黑客松 Demo；对现在想成为 AI 产品经理的我而言，它也是一个起点——让我开始理解，产品工作既要把模型能力转化为用户流程，也要为模型判断、资金风险、团队协作和最终表达承担责任。
